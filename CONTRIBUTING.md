# Contributing to Protoling

Thanks for helping. Protoling is early, so bug reports, ideas and small, focused pull requests are all valuable.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Ways to help

- **Report a bug** with the [bug report form](https://github.com/prashantrajm/protoling/issues/new?template=bug_report.yml). A minimal route file that shows the problem helps most.
- **Suggest an idea** with the [feature request form](https://github.com/prashantrajm/protoling/issues/new?template=feature_request.yml). Describe the interaction you're trying to prototype, not only the API you'd like.
- **Improve the docs.** The README and [AGENTS.md](AGENTS.md) are what most people read first.
- **Send a pull request.** For anything bigger than a small fix, open an issue first so we can agree on the approach before you spend time on it.

Security problems: please don't open a public issue. See [SECURITY.md](SECURITY.md).

## Principles

These shape what gets merged:

- **Code-first.** Prototypes are written in code, by people and by coding agents. The UI is for playing, comparing and handing off, not for authoring.
- **Plain TanStack Router.** A project's routes are ordinary TanStack route files. Protoling adds a thin layer (`StackScreen`, `useDismiss`, `useTabs`, `useMotion`, `useVariant` and typed `staticData`), not a navigation library or a framework of its own.
- **Native feel.** Navigation and motion should behave the way they do on a phone, iOS first.
- **Honest handoff.** Values exported to SwiftUI and Compose must match what the prototype actually runs, and be tested.

## Development setup

You need [Bun](https://bun.sh) 1.2 or later. To use `bun run snap`, you also need Google Chrome installed.

```bash
git clone https://github.com/prashantrajm/protoling.git
cd protoling
bun install
bun run dev
```

Open [http://localhost:3000](http://localhost:3000). The Orbit example in `projects/orbit` exercises most features; it's the quickest way to see a change working.

### Where things live

```
src/runtime/           the API prototypes import from @/runtime
src/components/app/    the host around every mini app: device, safe areas, phone menu
src/components/        play, boards, inspector, shell, ui (shadcn)
src/lib/               devices, motion maths, handoff, boards, workspace
src/routes/host/       Protoling's own pages
projects/orbit/        the example app
vite/                  project discovery and the read-only dev endpoint
scripts/snap.ts        renders app states to PNGs
```

`src/routeTree.gen.ts` is generated by the router plugin. Don't edit it by hand; it's committed so type checking works on a fresh clone.

## Making a change

1. Fork the repository and create a branch from `main`, e.g. `fix/sheet-drag` or `feat/android-back`.
2. Keep the pull request focused on one thing.
3. Add or update tests when you change behaviour in `src/lib` or `vite/`. Spring and handoff maths must stay covered.
4. For visual changes, check them with `bun run snap <project>/<path>` and add before/after screenshots to the pull request.
5. Add a line under **Unreleased** in [CHANGELOG.md](CHANGELOG.md) for anything a user would notice.
6. Run the checks below, then open the pull request and fill in the template.

### Checks

```bash
bun run lint        # Biome: lint and formatting
bun run typecheck   # TypeScript
bun run test        # Vitest
bun run build       # production build
```

`bun run format` fixes formatting. CI runs the same checks on every pull request.

### Style

- Formatting is Biome's job; don't argue with it.
- Comments explain *why*, not what the next line does.
- Commit messages: a short imperative subject ("Fix sheet dismiss on fast flicks"), then a body that explains the reason when it isn't obvious.
- Prototype colours stay independent of Protoling's own theme. Don't use Protoling's CSS variables inside `projects/`.
